## Exercício 1 — Inserção simples

### Comandos SQL

```sql
INSERT INTO categoria (nome) VALUES ('Informática');
INSERT INTO categoria (nome) VALUES ('Escritório');
INSERT INTO categoria (nome) VALUES ('Acessórios');
INSERT INTO categoria (nome) VALUES ('Eletrônicos');

SELECT * FROM categoria;
```

### Resultado esperado

| id_categoria | nome |
|--------------|------|
| 1 | Informática |
| 2 | Escritório |
| 3 | Acessórios |
| 4 | Eletrônicos |

### Análise

**O que foi informado por você:** apenas o nome de cada categoria (`Informática`, `Escritório`, `Acessórios`, `Eletrônicos`).

**O que foi gerado automaticamente:** o `id_categoria` (1, 2, 3 e 4). Isso acontece porque a coluna está definida como `GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`, ou seja, o PostgreSQL cria sozinho um número sequencial para cada linha nova.

## Exercício 2 — Inserindo produtos

### Comandos SQL

Usando os `id_categoria` do exercício anterior (Informática = 1, Escritório = 2, Acessórios = 3, Eletrônicos = 4):

```sql
INSERT INTO produto (nome, preco, estoque, id_categoria)
VALUES ('Teclado Mecânico', 250.00, 10, 1);

INSERT INTO produto (nome, preco, estoque, id_categoria)
VALUES ('Mouse Sem Fio', 120.00, 15, 1);

INSERT INTO produto (nome, preco, estoque, id_categoria)
VALUES ('Caderno', 25.90, 30, 2);

INSERT INTO produto (nome, preco, estoque, id_categoria)
VALUES ('Cabo USB-C', 39.90, 20, 3);

INSERT INTO produto (nome, preco, estoque, id_categoria)
VALUES ('Fone Bluetooth', 180.00, 8, 4);

SELECT * FROM produto;
```

### Resultado esperado

| id_produto | nome | preco | estoque | id_categoria |
|------------|------|-------|---------|--------------|
| 1 | Teclado Mecânico | 250,00 | 10 | 1 |
| 2 | Mouse Sem Fio | 120,00 | 15 | 1 |
| 3 | Caderno | 25,90 | 30 | 2 |
| 4 | Cabo USB-C | 39,90 | 20 | 3 |
| 5 | Fone Bluetooth | 180,00 | 8 | 4 |

### Análise

O `id_produto` foi preenchido automaticamente com 1, 2, 3, 4 e 5. Isso acontece porque essa coluna também é `GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`. O PostgreSQL vai somando 1 a cada novo produto inserido, sem você precisar informar.

## Exercício 4 — Utilizando `DEFAULT` e `RETURNING`

### Comando SQL

```sql
INSERT INTO produto (nome, preco, id_categoria)
VALUES ('Mousepad', 35.00, 1)
RETURNING *;
```

### Resultado esperado

| id_produto | nome | preco | estoque | id_categoria |
|------------|------|-------|---------|--------------|
| 10 | Mousepad | 35,00 | 0 | 1 |

### Respostas

1. **Qual valor foi atribuído a `estoque`?**
   O valor `0`.

2. **Por que esse valor foi utilizado?**
   Porque na criação da tabela a coluna `estoque` tem `DEFAULT 0`. Como não informamos o estoque, o PostgreSQL usou o valor padrão.

3. **Quem gerou `id_produto`?**
   O próprio PostgreSQL, através da `IDENTITY` da chave primária.

4. **Qual é a função do `RETURNING *`?**
   Ele devolve os dados da linha que acabou de ser inserida, incluindo os valores que o banco gerou automaticamente (como o `id_produto` e o `estoque` padrão). Serve para você conferir o resultado logo na hora.

## Exercício 5 — Tentando violar as regras do banco

Tentativas de inserção que quebram as restrições:

| Tentativa | Inserção aceita? | Restrição envolvida | Explique o motivo |
|-----------|------------------|---------------------|-------------------|
| Produto sem nome | **Não** | `NOT NULL` em `nome` | A coluna `nome` não pode ficar vazia. O banco rejeita porque falta um valor obrigatório. |
| Preço negativo | **Não** | `CHECK (preco >= 0)` | A regra `CHECK` impede que o preço seja menor que zero. |
| Estoque negativo | **Não** | `CHECK (estoque >= 0)` | A regra `CHECK` impede que o estoque seja menor que zero. |
| Categoria inexistente | **Não** | `FOREIGN KEY` (`fk_produto_categoria`) | O `id_categoria` informado não existe na tabela `categoria`. A chave estrangeira exige que o valor referenciado exista. |
| Categoria duplicada | **Não** | `UNIQUE` em `nome` | Já existe uma categoria com esse nome cadastrada. A restrição `UNIQUE` impede nomes repetidos. |

### Exemplos dos comandos que gerariam erro

```sql
-- A. Produto sem nome
INSERT INTO produto (preco, estoque, id_categoria)
VALUES (10.00, 5, 1);
-- ERRO: viola NOT NULL em nome

-- B. Preço negativo
INSERT INTO produto (nome, preco, estoque, id_categoria)
VALUES ('Produto X', -50.00, 10, 1);
-- ERRO: viola CHECK (preco >= 0)

-- C. Estoque negativo
INSERT INTO produto (nome, preco, estoque, id_categoria)
VALUES ('Produto Y', 10.00, -3, 1);
-- ERRO: viola CHECK (estoque >= 0)

-- D. Categoria inexistente
INSERT INTO produto (nome, preco, estoque, id_categoria)
VALUES ('Produto Z', 10.00, 5, 999);
-- ERRO: viola FOREIGN KEY (categoria 999 não existe)

-- E. Categoria duplicada
INSERT INTO categoria (nome)
VALUES ('Informática');
-- ERRO: viola UNIQUE (já existe categoria com esse nome)
```

## Conclusão

Esses exercícios mostram que o banco de dados não aceita qualquer coisa. Ele aplica as regras de integridade automaticamente:

- `PRIMARY KEY` e `IDENTITY` geram identificadores únicos sozinhos.
- `NOT NULL` obriga o preenchimento de campos importantes.
- `UNIQUE` impede valores repetidos.
- `CHECK` impede valores fora do permitido (como preço ou estoque negativo).
- `FOREIGN KEY` garante que relacionamentos entre tabelas façam sentido.
- `DEFAULT` preenche um valor padrão quando nada é informado.
- `RETURNING` mostra o que foi inserido, incluindo o que o banco criou sozinho.
